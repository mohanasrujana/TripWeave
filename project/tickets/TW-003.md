## Goal

Create the React client and prove that it can represent the API health request
through loading, success, and error states.

## What I have done

- Created a React 19 and TypeScript client with Vite under `apps/web`.
- Replaced the Vite starter screen with a small TripWeave API health view.
- Modeled request state as a TypeScript discriminated union so the UI handles
  loading, success, and error cases explicitly.
- Called `GET /api/health` when the component mounts.
- Checked non-success HTTP responses and rejected malformed JSON instead of
  treating every response as healthy.
- Used `AbortController` to cancel the request when the component unmounts.
- Added accessible live status and alert roles for health feedback.
- Configured the Vite development proxy to send `/api` requests to
  `http://localhost:8080`, avoiding a separate frontend URL in application code.
- Added Vitest, jsdom, React Testing Library, and jest-dom.
- Added component tests for loading, successful `UP` response, and network
  failure states.
- Added Prettier configuration and scripts for formatting, tests, and the full
  frontend check.

## State flow

```text
Component mounts
  -> loading: "Checking API health..."
  -> success: "API status: UP"
  -> error:   "Unable to reach the API: <reason>"
```

## Important implementation choices

- I used one discriminated union instead of several booleans. This prevents
  impossible combinations such as loading and error being true together.
- I validate the response at runtime because TypeScript types do not validate
  data received over HTTP.
- The development proxy keeps the fetch call relative (`/api/health`) and lets
  Vite forward it to the backend during local development.

## Manual verification

- With the API and Vite running, the browser displayed `API status: UP`.
- With Vite running and the API stopped, the browser displayed
  `Unable to reach the API: API returned status 502`.
- The loading state is covered by the component test because it is transient in
  the browser.
